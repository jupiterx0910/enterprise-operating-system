# v0.5 Pilot Runner Design / 首轮真实模型实验设计

## Goal / 目标

Build and execute the first auditable **NATIVE vs EOS_ENABLED** Candidate experiment for Enterprise Operating System.

本版本不追求“大模型排行榜”，而是先回答一个更重要的问题：

> **同一个模型，在相同案例、相同运行参数和相同推理环境下，加载 EOS 后，企业经营推理是否出现可测量的增益？**

The v0.5 pilot must produce real raw outputs, reproducible run metadata, rubric scorecards, and a Candidate-level Skill Lift result without overstating it as Verified.

---

## Experiment scope / 实验范围

### Model

- Repository: `Qwen/Qwen3-8B`
- Model revision: **must be pinned to an exact Hugging Face commit SHA at execution time**
- Loading: Transformers-compatible causal language model
- Precision: BF16 when hardware supports it
- Internet access during inference: not required after model/case assets are resolved

If the pinned model cannot load on the selected hardware, **stop the experiment** and record the failure. Do not silently substitute another model.

### Cases

Run only the five public real-world cases introduced in v0.4:

1. `21-wells-fargo-incentive-distortion`
2. `22-target-canada-operating-model`
3. `23-uber-culture-governance`
4. `24-equifax-accountability-gap`
5. `25-boeing-737-max-governance`

### Conditions

Two paired conditions:

- `NATIVE`
- `EOS_ENABLED`

One trial per case per condition:

```text
5 cases × 2 conditions × 1 trial = 10 generations
```

This qualifies only as **Candidate / Pilot**, never Verified.

---

## Experimental isolation / 变量隔离

The two conditions must hold constant:

- exact model repository and revision;
- tokenizer revision;
- generation parameters;
- max output tokens;
- case snapshot;
- case prompt;
- evidence packet;
- system baseline;
- hardware class;
- inference library versions;
- random seed if exposed and honored;
- no tools during answer generation;
- no web access during answer generation.

The **only intentional treatment difference** is EOS Skill context.

### Baseline system prompt

The NATIVE system prompt must be minimal and generic:

> You are an enterprise operating advisor. Analyze the case using only the evidence provided. Distinguish facts, inference, assumptions, and unknowns. Give a decision-oriented answer and do not invent missing facts.

This avoids intentionally handicapping the baseline.

### EOS treatment

The EOS condition uses the exact same baseline system prompt plus a deterministic Skill bundle generated from the canonical runtime:

```text
skills/enterprise-operating-system/
├── SKILL.md
├── engines/
├── references/
└── templates/
```

The runner must:

1. enumerate canonical runtime Markdown files in sorted path order;
2. preserve file path headings;
3. concatenate their exact committed contents;
4. compute SHA-256 of the final bundle;
5. record bundle token count;
6. inject the bundle only in `EOS_ENABLED`.

Do not manually summarize or edit the Skill before injection.

This means the treatment is the installable EOS artifact itself, not a hand-written “better prompt”.

---

## Prompt construction / Prompt 构造

For each case, expose only:

- `Context / 背景`
- `Evidence / 证据`
- `Prompt / 用户问题`

Do **not** expose:

- `Expected reasoning / 期望推理`
- `Forbidden shortcuts / 禁止捷径`
- `Decision criteria / 决策标准`
- `Evaluation notes / 评测说明`

The runner must parse these sections from the committed benchmark file instead of duplicating case text into code.

---

## Generation contract / 生成协议

The pilot runner records all generation parameters in the manifest.

Default pilot settings:

```yaml
do_sample: false
temperature: null
top_p: null
seed: 42
max_new_tokens: 1800
```

Rationale:

- deterministic decoding minimizes pilot variance;
- one-trial Candidate results should not be dominated by sampling noise;
- future Verified runs may introduce repeated sampled trials under a separately versioned protocol.

If the model/runtime internally requires a temperature value, record the actual value rather than pretending it is null.

---

## Runtime / 运行环境

Execution target: Hugging Face Jobs.

The job must be self-contained and write artifacts to an output directory that can be recovered after execution.

Minimum recorded runtime metadata:

```yaml
python:
torch:
transformers:
accelerate:
hardware:
cuda:
model_revision:
tokenizer_revision:
case_snapshot:
skill_commit:
runner_commit:
```

### Cost guardrail

This is a deliberately small paid-compute pilot.

Stop conditions:

- model download/load repeatedly fails;
- hardware is insufficient;
- projected execution expands beyond the defined 10 generations;
- the runner attempts to launch another paid job automatically;
- outputs are incomplete or unrecoverable.

**One approved pilot job does not authorize retries on progressively larger hardware.**

A failed paid job is reported before any second paid job is launched.

## Scoring / 评分

Use the existing 12-point rubric:

1. Evidence discipline
2. Causal diagnosis
3. System thinking
4. Decision quality
5. Execution design
6. AI-native redesign

Each dimension remains 0–2.

### First-pass evaluator

The pilot may use an **LLM-assisted rubric pass** to create scorecards, but:

- every dimension needs a short evidence citation from the raw output;
- hard-fail reasons must quote or identify the relevant answer behavior;
- aggregate results must say `evaluator: llm-assisted`;
- the result remains Candidate;
- no “Verified” label is allowed.

This v0.5 pilot does **not** claim independent human adjudication.

### Aggregate metrics

Calculate:

```text
Native Mean
EOS Mean
Skill Lift = EOS Mean - Native Mean

Native Hard-Fail Rate
EOS Hard-Fail Rate
Hard-Fail Reduction = Native HF% - EOS HF%

Per-dimension Native Mean
Per-dimension EOS Mean
Per-dimension Lift
```

Also publish per-case paired deltas.

---

## Interpretation guardrails / 解释约束

The pilot supports only:

> “On this pinned model, these five public cases, this runner version, and this deterministic one-trial protocol, EOS changed the measured reasoning score by X.”

It does **not** support:

- “EOS improves all models.”
- “EOS improves real companies by X%.”
- “EOS is statistically significant.”
- “EOS is Verified.”
- “Qwen3-8B is the best enterprise model.”
- causal claims beyond the paired experimental treatment.

Because the five cases are public historical cases, they are not contamination-resistant.

## Runner architecture / Runner 架构

Add a small Python runner with focused responsibilities:

```text
benchmark/runner/
├── README.md
├── requirements.txt
├── extract_case.py
├── build_skill_bundle.py
├── run_pilot.py
├── validate_artifacts.py
└── tests/
```

Responsibilities:

### `extract_case.py`

- parse only Context, Evidence, Prompt;
- fail if any required section is missing;
- never leak expected reasoning or evaluator sections.

### `build_skill_bundle.py`

- read canonical runtime only;
- stable path ordering;
- exact file contents;
- SHA-256;
- token-count metadata.

### `run_pilot.py`

- pin model and tokenizer revision;
- build paired prompts;
- execute 10 generations;
- save each raw output immediately;
- save manifests even if later cases fail;
- never score inside generation.

### `validate_artifacts.py`

- verify all ten outputs exist;
- verify model/config equality across conditions;
- verify only treatment difference is `skill_loaded` and Skill bundle metadata;
- reject a Candidate result if pairing is incomplete.

Scoring remains a separate post-generation step so generation failures cannot be hidden by aggregate code.

---

## CI / 测试

Core CI must remain free of paid inference.

CI should test:

- case parser excludes hidden evaluation sections;
- Skill bundle is stable and changes hash when canonical Skill changes;
- paired manifests reject model/config drift;
- incomplete 9/10 output sets fail validation;
- Candidate cannot become Verified by editing a summary string;
- no paid HF Job launches from GitHub Actions.

Use fixtures and a fake generator for CI.

---

## Publication / 发布

The first real Candidate result may be committed only after:

1. the paid Job has completed;
2. all ten raw outputs are recovered;
3. artifact validation passes;
4. scorecards exist for all ten outputs;
5. aggregate math is independently recomputed by the validation script;
6. public summary states the exact limitations.

The leaderboard adds a **Pilot / Candidate** section separate from Verified.

Verified remains empty after v0.5 pilot.

---

## Success criteria / 成功标准

v0.5 succeeds if:

- one pinned model completes 10 paired generations;
- raw outputs are preserved;
- NATIVE/EOS configuration equality is machine-validated;
- Skill bundle provenance is reproducible;
- scorecards are auditable;
- Skill Lift and Hard-Fail Reduction are computed from raw scorecards;
- no fake or inferred model result is published;
- existing Skill / Benchmark / v0.4 CI remains green.

The project gains more value from **one trustworthy Candidate result** than from ten unverifiable leaderboard rows.
